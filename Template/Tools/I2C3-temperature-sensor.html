Emulated temperature sensor: binary library and API

This project includes a temperature sensor emulator on I2C3. It uses the microcontroller's internal ADC temperature sensor and presents it through an I2C interface. The emulator has been implemented as a binary static library and is already integrated into the STM32CubeIDE project. The library has been implemented for the NUCLEO-L452RE development board, which uses the STM32L452RE microcontroller.

Sensor pins

On the NUCLEO-L452RE board, the emulated sensor is available on the following STM32 I2C3 pins:

MCU pin I2C3 signal Function
PC0 SCL Serial clock
PC1 SDA Serial data

Both pins are configured as open-drain outputs with no internal pull-ups enabled (GPIO_NOPULL). The firmware does not provide pull-ups on PC0 or PC1; the connected I2C bus must provide external pull-up resistors.

The library and its public interface

A binary library contains code that has already been compiled. In this project, that code is stored in a .a archive. During a firmware build, the linker takes the required code from the archive and combines it with the application to produce the executable firmware.

The corresponding .h file declares the library's application programming interface (API): the public functions and definitions available to application code. The header describes the interface; the archive supplies the compiled implementation. Both are part of the library integration.

Project file Purpose
libtemperature_slave.a Compiled implementation of the emulator.
temperature_slave.h API reference: public definitions, function declarations, and interface comments.

Read temperature_slave.h for the emulator API. Its USER_Definitions and PUBLIC_API sections identify the public constants and entry points. Read the declarations together with their comments to understand the interface and its constraints.

Working with a developer API

The header is written at the level used in firmware development. Function names, parameter lists, return types, symbolic constants, and comments are part of the information you are expected to interpret when reading an API. The manual provides orientation; the header remains the reference for the library interface. The register transactions below describe the I2C interface seen by a master; they are separate from the C API used by the firmware.

CubeIDE's Debug and Release configurations link the supplied archive. Changing a declaration in the header does not change the binary implementation: the header and library must remain compatible.

The archive supplied here targets the STM32L452 Cortex-M4 with the project's hard-float settings. It is a component of this firmware project, rather than an executable program that runs independently on a computer.

Firmware integration

The project calls temperature_slave_init() after ADC startup and calibration. This library entry point initializes I2C3 and starts the emulator; the application does not call MX_I2C3_Init() separately. The project HAL MSP supplies the I2C3 clock, pin and NVIC configuration, with no internal pull-ups on PC0 or PC1. Both I2C3_EV_IRQHandler and I2C3_ER_IRQHandler dispatch to the library. The emulator requires no main-loop service. These entry points are supplied by the binary library; their declarations and interface comments are in temperature_slave.h.

Using the sensor through I2C registers

The sensor's 7-bit slave address is 0x48. A logic analyzer showing full address bytes will display 0x90 for a write and 0x91 for a read. When a master API expects a 7-bit address, supply 0x48; STM32 HAL expects that value shifted left by one bit (0x48 << 1). The master must support clock stretching while the emulator acquires a fresh temperature sample.

The reported temperature is the MCU's internal die temperature, which can differ from room temperature. The sensor starts with readings disabled.

Register Access Size Meaning
0x00 Read/write 1 byte Control: bit 0 enables readings (1) or disables them (0). Other bits read as zero and are ignored on writes. Reset value: 0x00.
0x01 Read only 2 bytes Signed temperature in hundredths of a degree Celsius, most significant byte first. 0x8000 indicates an unavailable reading.

Enable or disable readings

To enable readings, send a write to address 0x48 with the two data bytes 00 01. The first byte selects the control register; the second sets its value. To disable readings, send 00 00 instead. Disabling readings does not remove the device from the bus: control reads remain available, and temperature reads return 80 00.

Read a register

A register read first writes a one-byte register pointer, then reads that register's data. For temperature, the transaction is:

START -> 0x48 + WRITE -> 0x01 -> repeated START -> 0x48 + READ
      -> temperature MSB -> temperature LSB -> STOP

The master ACKs the first returned byte and NACKs the second before STOP. For control, select 0x00 and read one byte, NACKing that byte before STOP. A STOP between pointer selection and the read is also supported. The pointer is retained, so subsequent reads can use the previously selected register. Each temperature read takes a fresh sample; its two bytes form one snapshot.

Decode the temperature

Combine the bytes as (MSB << 8) | LSB. First check for 0x8000: it means readings are disabled, a conversion failed, or the ADC is temporarily unavailable. Do not interpret that value as a temperature.

Otherwise interpret the combined value as a signed 16-bit two's-complement number and divide by 100 to obtain degrees Celsius.

Returned bytes Signed value Temperature
09 C4 2500 25.00 degrees C
FF 9C -100 -1.00 degrees C
80 00 Reserved Reading unavailable

Registers do not auto-increment. Writes to the temperature register are ignored. Unknown registers return FF; bytes read beyond a register's defined size also return FF. An I2C transfer error is separate from the 80 00 value: the master must check whether the transfer succeeded before decoding the returned bytes.
